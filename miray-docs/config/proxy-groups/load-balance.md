# load-balance

Распределяет соединения по живым узлам группы.

```yaml
proxy-groups:
  - name: balance
    type: load-balance
    proxies: [node-a, node-b, node-c]
    url: https://www.gstatic.com/generate_204
    interval: 300
    strategy: consistent-hashing
    # hash-key: in-user
```

Остальные поля — [общие](index.md).

> **miray:** если выбранный стратегией узел не подключился вовремя или вернул ошибку, соединение уходит на следующий живой узел группы по порядку, не дожидаясь таймаута. Стратегия при этом не меняется: хеш, привязки `sticky-sessions` и очередь `round-robin` остаются прежними. Подробно — [переключение при отказе узла](index.md#переключение-при-отказе-узла).

## strategy

Как выбирать узел:

- `consistent-hashing` (по умолчанию) — соединения к одной цели идут через один узел; при выпадении узла переезжают только его цели;
- `round-robin` — по очереди;
- `sticky-sessions` — соединения с одного адреса источника к одной цели идут через один узел, привязка держится 10 минут.

Для цели-домена ключом служит домен второго уровня (`api.example.com` → `example.com`), для IP — сам адрес.

## hash-key

Чем заменить ключ у `consistent-hashing` и `sticky-sessions`:

- `in-user` — имя пользователя, под которым клиент вошёл на вход ядра (то же, что проверяют правила `IN-USER`). Узел не меняется, когда задача клиента ходит по разным доменам. Соединения без входа по пользователю используют ключ стратегии.

Не задано — ключ стратегии. С `round-robin` поле — ошибка конфига: эта стратегия ничего не хеширует.
